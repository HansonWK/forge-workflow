# Forge Workflow — Design Spec

## Overview

Forge Workflow is an open-source, opinionated AI-assisted development workflow for Claude Code. It ships as a set of `.md` command and agent files that users install into their `.claude/` directory. The package ships with sensible example values that make the files readable and understandable out of the box, and `/install` rewrites them with the real values. The examples serve as documentation of intent too.

### Shared Team Workflow

Forge Workflow is designed to be **committed to your repository** so that every developer on the team uses the same AI-assisted workflow. Rather than each developer maintaining their own personal Claude commands and agents, the team shares a single set that lives in version control.

This means:
- **Consistency** — every developer gets the same workflow, commands, and quality gates
- **Continuous improvement** — any developer can update a workflow file, submit a PR, and the team reviews and approves the change like any other code
- **Onboarding** — new team members get the full workflow immediately by cloning the repo
- **Evolution** — the workflow improves over time as the team discovers what works and what doesn't, with every change tracked in git history

Developers can ask Claude to update its own workflow files (e.g., "update the security audit to also check for X"), then commit and PR that change for team review.

## Distribution

Two supported installation methods:

1. **npm package** — `npx forge-workflow install` copies files into `.claude/` and runs the interactive setup
2. **Manual copy** — Users copy files (or just `commands/install.md`) into their `.claude/commands/` directory, then run `/install`

Both paths converge on the same `/install` command. The `install.md` file must be at `.claude/commands/install.md` in the user's project for Claude Code to recognize it as the `/install` slash command.

## The `/install` Command

### Phase 1 — Scan

Claude reads the codebase to detect:

- Language and framework (from `package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`, etc.)
- Test runner, linter, formatter
- Package manager
- Git remote (GitHub, GitLab, Bitbucket)
- Existing `.claude/` directory and `claude.md`
- Existing forge-workflow files (fresh install vs update)
- Monorepo vs single project

### Phase 2 — Present Findings & Ask Questions

Claude presents what it found:

> "I detected a TypeScript/React project using Vitest, ESLint, Prettier, hosted on GitHub."

Then asks only what it couldn't determine:

- **Ticket tracker:** "Will you use Jira, GitHub Issues, or another system?"
  - If Jira: run setup wizard (email, instance URL, API token → saved to `~/AI/config/jira.env`)
  - If GitHub Issues: no additional setup needed
  - If other: Claude generates a new `ticket-tracker.md` agent using the existing Jira/GitHub examples as a base
- **Branch naming convention:** confirm or customize the default (`<TICKET-ID>-<kebab-case-summary>`)
- Any other gaps in detection

### Phase 3 — Install/Update

1. **Generate `workflow-config.md`** with all collected project information
2. **Install command and agent files:**
   - If files don't exist: copy from package into `.claude/`
   - If files already exist: read each one and update with real project values (e.g., replace `PROJ-1234` with actual Jira prefix, replace `npm run test` with `pnpm vitest`)
3. **Handle `claude.md`:**
   - If no `claude.md` exists: create one with core principles adapted to the detected stack, plus workflow entry points
   - If `claude.md` exists: append a `# Forge Workflow` section with available commands, working directories, and workflow principles

### Phase 4 — Verify

- List what was installed or updated
- Suggest running `/workflow` to see available commands

## `workflow-config.md`

Generated by `/install` at `.claude/docs/workflow-config.md` in the user's project. Serves as a reference for what was configured and is read by commands/agents when they need project-specific information. Example:

```markdown
# Workflow Configuration

## Project
- **Language:** TypeScript
- **Framework:** React / Next.js
- **Monorepo:** No
- **Package manager:** pnpm

## Commands
- **Test:** pnpm test
- **Lint:** pnpm lint
- **Format:** pnpm format
- **Format check:** pnpm format:check
- **Build:** pnpm build

## Ticket Tracker
- **System:** Jira
- **Base URL:** https://mycompany.atlassian.net
- **Project prefix:** PROJ
- **Credentials:** ~/AI/config/jira.env

## Git
- **Hosting:** GitHub
- **Default branch:** main
- **Branch convention:** <TICKET-ID>-<kebab-case-summary>

## Working Directories
- **AI temp files:** .claude/temp/
- **AI docs:** .claude/docs/

## Forge Workflow
- **Version:** 1.0.0
```

## Versioning & Updates

`workflow-config.md` includes a `Version` field tracking the installed forge-workflow version. When `/install` detects existing forge-workflow files:

1. It reads the current version from `workflow-config.md`
2. Compares against the package version being installed
3. For updates: reads each existing file, identifies user customizations vs stale shipped content by comparing against the previous version's defaults, and merges — preserving user changes while applying new workflow improvements
4. Presents a summary of what changed and asks for confirmation before writing

If Claude cannot confidently distinguish a user edit from shipped content, it asks the user.

## Example Values Mapping

Commands and agents ship with these example values. `/install` replaces them based on scan results and user answers:

| Example Value | Replaced With | Source |
|---|---|---|
| `PROJ-1234` | Actual ticket prefix (e.g., `NG20-1234`) | Ticket tracker config |
| `npm run test` | Actual test command (e.g., `pnpm vitest`) | Package manager + test runner detection |
| `npm run lint` | Actual lint command | Package scripts detection |
| `npm run format` / `format:check` | Actual format commands | Package scripts detection |
| `https://mycompany.atlassian.net` | Actual Jira instance URL | User input during install |
| `~/AI/config/jira.env` | Credentials path | User input or default |
| React/TypeScript/Jest examples in agents | Framework-specific equivalents | Language/framework detection |
| `apps/services/` paths | Actual project structure paths or removed | Codebase scan |

For agents like `test-writer.md` and `security-auditor.md` where the shipped examples are deeply framework-specific, `/install` performs a more substantial rewrite — essentially regenerating the file using the shipped version as a structural template while adapting all framework references, test patterns, and conventions to match the detected project.

## Terminology

This workflow uses **"subtask"** consistently to refer to individual units of work within a plan. Each subtask maps to roughly one commit. The planner agent breaks work into subtasks, and `/next` cycles through them.

## MCP Tool References

Some agents reference optional MCP tools (Memory MCP, GitHub MCP). These are treated as optional enhancements:

- If the user has the MCP server configured, agents will use the tools (e.g., `get_issue`, `search_issues`)
- If not available, agents gracefully skip those steps
- `/install` does not set up MCP servers — users configure these independently if desired

## `claude.md` Strategy

### New project (no `claude.md`)

`/install` creates one with:
- Core coding principles adapted to detected language/framework
- Testing philosophy (black-box, predict-then-verify)
- Planning conventions (plan files in `.claude/temp/`)
- Permissions section
- Workflow entry points

### Existing project (has `claude.md`)

`/install` appends a clearly marked section:

```markdown
# Forge Workflow

This project uses forge-workflow for AI-assisted development.

## Available Commands
- `/begin` — Start new work (research → plan → signoff)
- `/next` — Execute next subtask
- `/status` — View progress dashboard
- `/resume` — Resume existing plan
- `/pr` — Prepare and create pull request
- `/cr` — Code review
- `/security` — Security audit
- `/workflow` — See all commands

## Working Directories
- `.claude/temp/` — AI workspace for plans, research, status files
- `.claude/docs/workflow-config.md` — Workflow configuration

## Workflow Principles
- All plans live in `.claude/temp/<slug>/plan.md`
- Claude does not commit or push without explicit request
- All .md files created during work go to `.claude/temp/`
```

## Ticket Tracker Integration

Supported at launch:
- **Jira** — ported from existing integration with setup wizard
- **GitHub Issues** — built-in via `gh` CLI, no credentials needed
- **Other** — Claude generates a new `ticket-tracker.md` using Jira and GitHub Issues agents as examples

The `ticket-tracker.md` agent is the single integration point. All commands reference this agent for ticket operations rather than calling Jira/GitHub directly.

## Core Workflow

The full opinionated workflow installs by default:

```
/begin → /research → /plan → /signoff → /next (cycles: /dev → /review → /present) → /security → /pr
```

Users can progressively customize by telling Claude to update its own workflow files.

## `.gitignore` Recommendations

`/install` should check for and suggest adding to `.gitignore`:

- `.claude/temp/` — ephemeral work files, plans in progress, potentially sensitive ticket context
- `.claude/settings.local.json` — personal settings that may contain paths or preferences

The workflow files themselves (commands, agents, docs) should be committed so the whole team shares the workflow.

## `settings.json`

`/install` does not generate or modify `.claude/settings.json` or `.claude/settings.local.json`. These are Claude Code configuration files that users manage independently. The README should document recommended settings (e.g., permissions for `.claude/temp/` workspace, formatter hooks) but the install does not touch them.

## Design Principles

1. **Files are prompts, not code** — no templating engine, no placeholders at runtime. `/install` uses Claude's understanding to rewrite files with real values.
2. **Self-extending** — users customize by asking Claude to modify the workflow files directly.
3. **Opinionated by default** — ship the full workflow, let users evolve it.
4. **Respect existing work** — `/install` never overwrites `claude.md`, only appends.
5. **Example values as documentation** — shipped files use readable examples (`PROJ-1234`, `npm run test`) that demonstrate intent and get replaced during install.
6. **Shared team workflow** — workflow files are committed to the repo so every developer uses the same commands, agents, and quality gates. Changes go through PRs like any other code.
